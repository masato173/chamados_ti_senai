1. APRESENTAÇÃO DO PROJETO
======================================================================

1.1. Nome do projeto

Sistema Web de Gerenciamento e Controle de Chamados de Suporte Técnico de TI.

1.2. Objetivo geral

Desenvolver um sistema web para centralizar e organizar as solicitações de
suporte técnico de TI, permitindo que usuários registrem problemas,
acompanhem seus chamados e consultem o andamento dos atendimentos.

A aplicação também permitirá que administradores gerenciem usuários,
atualizem chamados, atribuam responsáveis, registrem soluções e acompanhem
o histórico de atendimentos.

O sistema deverá proporcionar maior organização, segurança, controle e
rastreabilidade das solicitações de suporte técnico.

1.3. Assunto do projeto

O projeto aborda o desenvolvimento de uma aplicação web voltada ao
gerenciamento de chamados de suporte técnico, utilizando Java, Spring Boot,
Spring Security e Spring Data JPA.

O foco está na automatização do processo de abertura, acompanhamento e
encerramento de solicitações, com controle de acesso por perfil, persistência
de dados e registro das atividades realizadas.

1.4. Justificativa

A utilização de um sistema centralizado permite substituir controles manuais
e informações dispersas por um processo organizado de gerenciamento de
chamados.

Com isso, torna-se possível acompanhar solicitações, identificar
responsáveis, registrar soluções, consultar históricos e manter informações
acessíveis de maneira estruturada.

1.5. Resultado esperado

- Centralizar as solicitações de suporte.
- Organizar os chamados por categoria.
- Acompanhar o status dos atendimentos.
- Identificar os responsáveis.
- Registrar soluções e observações.
- Consultar históricos.
- Controlar usuários e permissões.
- Preservar a rastreabilidade das operações.

2. FUNCIONAMENTO GERAL
======================================================================

O sistema terá dois perfis principais: usuário comum e administrador.

USUÁRIO COMUM
- Abrir chamados.
- Consultar seus próprios chamados.
- Visualizar detalhes permitidos.
- Acompanhar o andamento dos chamados.
- Acessar o próprio perfil.
- Consultar o próprio histórico de chamados.

ADMINISTRADOR
- Cadastrar, consultar, atualizar e excluir logicamente usuários.
- Consultar chamados.
- Visualizar detalhes dos chamados.
- Atualizar informações dos chamados.
- Alterar status.
- Definir responsáveis.
- Registrar atendimentos.
- Encerrar chamados.
- Consultar o histórico de atendimentos.
- Consultar registros de auditoria.

Fluxo geral:
1. O usuário realiza login.
2. O sistema identifica seu perfil.
3. O usuário ou administrador registra um chamado.
4. O sistema identifica automaticamente o solicitante, gera o ID,
   registra a data e define o status inicial ABERTO.
5. O administrador consulta o chamado e define o responsável.
6. O status pode ser alterado para EM_ANDAMENTO.
7. O administrador registra o atendimento e a solução.
8. O sistema altera o status para FECHADO e registra o histórico.

6. ESTRUTURA DOS CHAMADOS
======================================================================

Cada chamado deverá possuir os seguintes campos:

Campo             Descrição
ID                Identificador único do chamado, gerado automaticamente.
Solicitante       Usuário autenticado que abriu o chamado.
Local             Local onde ocorre o problema.
Categoria         Tipo da solicitação.
Problema          Descrição do problema informado.
Observação        Informações adicionais, quando houver.
Status            Situação atual do chamado.
Aberto quando     Data e hora de abertura preenchidas automaticamente.
Responsável       Administrador responsável pelo atendimento.
Ação              Operações disponíveis conforme as permissões.

O campo "Ação" representa operações da interface e não precisa ser uma
coluna armazenada na tabela do banco de dados.

6.1. Abertura automática

Ao registrar um chamado, o backend deverá:
1. Gerar o ID automaticamente.
2. Identificar o solicitante autenticado.
3. Registrar a data e hora de abertura.
4. Definir o status inicial como ABERTO.
5. Salvar as informações do chamado.
6. Registrar a abertura no histórico de auditoria.

O solicitante não deverá ser escolhido livremente pelo frontend. O backend
deverá obter a identidade do usuário por meio do contexto de segurança.

7. CATEGORIAS E STATUS
======================================================================

7.1. Categorias disponíveis

1. Impressora.
2. Rede / Internet.
3. Computador / Notebook.
4. Periférico ou cabo com defeito.
5. Sistema / Software.
6. Acesso ou senha.
7. Solicitação de material ou equipamento.
8. Outro.

O usuário deverá selecionar uma categoria no formulário de abertura.
Categorias utilizadas em chamados antigos deverão ser preservadas. Uma
categoria inativa não poderá ser selecionada em novos chamados.

7.2. Status disponíveis

ABERTO
Chamado registrado e aguardando atendimento.

EM_ANDAMENTO
Chamado que está sendo atendido.

FECHADO
Atendimento encerrado.

O encerramento deverá exigir o registro de uma solução.
Um chamado fechado não deverá ser encerrado novamente sem uma operação
autorizada de reabertura.

======================================================================
8. GERENCIAMENTO DE USUÁRIOS
======================================================================

8.1. Cadastro

O administrador poderá cadastrar novos usuários.

Dados previstos:
- ID.
- Nome.
- Login.
- Senha.
- Perfil.
- Situação da conta.

8.2. Atualização

O administrador poderá atualizar os dados permitidos de um usuário.
A alteração de senha deverá possuir fluxo próprio e armazenar a nova senha
com BCrypt. Senhas nunca deverão ser retornadas pela API.

8.3. Exclusão

A exclusão será lógica, por meio da desativação da conta e do preenchimento
de um campo de data de exclusão. Os registros relacionados deverão ser
preservados.

8.4. Proteção do último administrador

Antes de desativar ou excluir logicamente um administrador, o backend deverá
verificar quantos administradores ativos existem.

- Se existirem outros administradores ativos, a operação poderá ser permitida,
  desde que as demais regras sejam atendidas.
- Se existir apenas um administrador ativo, sua desativação deverá ser
  impedida.

A verificação deverá ser transacional e usar bloqueio apropriado para reduzir
o risco de duas operações simultâneas desativarem os últimos administradores.

9. GERENCIAMENTO DE CHAMADOS
======================================================================

9.1. Abrir chamado

Acesso: usuário comum e administrador.

Campos do formulário:
- Solicitante: identificado automaticamente pelo backend.
- Local.
- Categoria: seleção de uma das categorias disponíveis.
- Problema.
- Observação.

Botão: REGISTRAR CHAMADO.

9.2. Visualizar chamados

O sistema deverá apresentar uma tabela com informações como:

ID | Solicitante | Categoria | Status | Responsável | Ação

O usuário comum visualizará apenas seus próprios chamados. O administrador
poderá consultar todos os chamados ativos, respeitando filtros e paginação.

9.3. Detalhes do chamado

O detalhe deverá apresentar os dados do chamado, o solicitante, a categoria,
o problema, as observações, o status, as datas, o responsável e os registros
de atendimento permitidos ao perfil autenticado.

9.4. Atualizar chamado

Acesso: somente administrador.

O administrador poderá:
- Atualizar problema.
- Atualizar observação.
- Alterar categoria, quando permitido.
- Alterar status.
- Definir ou atualizar responsável.

As alterações relevantes deverão gerar registros de auditoria com o valor
anterior e o novo valor.

9.5. Excluir chamado

Acesso: somente administrador.

A exclusão deverá ser lógica, usando um campo de data de exclusão. Os
atendimentos e históricos deverão permanecer preservados.

10. ATENDIMENTOS E ENCERRAMENTO
======================================================================

10.1. Histórico de atendimentos

Acesso: somente administrador.

Criar a funcionalidade/botão "Histórico de Atendimentos", com tabela
filtrável contendo, quando aplicável:
- ID do atendimento.
- ID do chamado.
- Solicitante.
- Responsável.
- Categoria.
- Status atual.
- Data de abertura.
- Data do atendimento.
- Solução registrada.

Filtros previstos:
- ID do chamado.
- Nome do solicitante.
- Responsável.
- Categoria.
- Status.
- Período.

10.2. Encerrar chamado

Acesso: somente administrador.

Campos:
- ID do chamado.
- Responsável.
- Observação.
- O que foi resolvido (solução).

Botão: REGISTRAR ATENDIMENTO.

10.3. Regras de encerramento

Ao registrar o atendimento, o sistema deverá:
1. Verificar se o chamado existe e não está excluído.
2. Verificar se o status permite encerramento.
3. Identificar o administrador autenticado.
4. Exigir uma solução preenchida.
5. Registrar o atendimento.
6. Atualizar o status do chamado para FECHADO.
7. Registrar a alteração no histórico.
8. Confirmar as operações na mesma transação.

Os atendimentos anteriores deverão ser preservados. Um novo atendimento
não deverá sobrescrever o registro de atendimento anterior.

12. MODELAGEM DO BANCO DE DADOS
======================================================================

Banco previsto: PostgreSQL.

O banco será relacional e utilizará chaves primárias, chaves estrangeiras,
restrições e índices para manter a integridade dos dados.

Entidades principais:
- Usuario: tabela usuarios.
- Categoria: tabela categorias.
- Chamado: tabela chamados.
- Atendimento: tabela atendimentos.
- HistoricoChamado: tabela historico_chamado.

12.1. Relacionamentos

- Um usuário pode solicitar vários chamados.
- Um usuário administrador pode ser responsável por vários chamados.
- Uma categoria pode estar associada a vários chamados.
- Um chamado pode possuir vários atendimentos.
- Um chamado pode possuir vários registros de histórico.
- Um usuário pode realizar vários atendimentos.
- Um usuário pode executar várias operações registradas no histórico.

12.2. Modelo textual de relacionamento

USUARIO 1 -------- N CHAMADO (solicitante)
USUARIO 1 -------- N CHAMADO (responsável, quando definido)
CATEGORIA 1 ------ N CHAMADO
CHAMADO 1 -------- N ATENDIMENTO
USUARIO 1 -------- N ATENDIMENTO (responsável)
CHAMADO 1 -------- N HISTORICO_CHAMADO
USUARIO 1 -------- N HISTORICO_CHAMADO (autor da operação)

13. ENTIDADES E ATRIBUTOS DO BANCO DE DADOS
======================================================================

13.1. Entidade Usuario
Tabela: usuarios

Campo          Tipo PostgreSQL      Regra
id             BIGINT               PK, identidade automática
nome           VARCHAR(150)         NOT NULL
login          VARCHAR(150)         NOT NULL, UNIQUE
senha          VARCHAR(255)         NOT NULL
perfil         VARCHAR(20)          NOT NULL: USER ou ADMIN
ativo          BOOLEAN              NOT NULL, DEFAULT TRUE
criado_em      TIMESTAMPTZ          NOT NULL, DEFAULT CURRENT_TIMESTAMP
atualizado_em  TIMESTAMPTZ          Atualizado pela aplicação
excluido_em    TIMESTAMPTZ          NULL; preenchido na exclusão lógica

Regras:
- O login não poderá ser repetido.
- A senha deverá ser armazenada com BCrypt.
- O perfil definirá as permissões.
- Usuários excluídos logicamente não poderão autenticar.
- O último administrador ativo não poderá ser desativado.

13.2. Entidade Categoria
Tabela: categorias

Campo   Tipo PostgreSQL   Regra
id      BIGINT            PK, identidade automática
nome    VARCHAR(100)      NOT NULL, UNIQUE
ativa   BOOLEAN           NOT NULL, DEFAULT TRUE

Regras:
- Não permitir categorias duplicadas.
- Categorias inativas não poderão ser usadas em novos chamados.
- Categorias utilizadas anteriormente deverão ser preservadas.

13.3. Entidade Chamado
Tabela: chamados

Campo             Tipo PostgreSQL      Regra
id                BIGINT               PK, identidade automática
solicitante_id    BIGINT               FK para usuarios, obrigatório
categoria_id      BIGINT               FK para categorias, obrigatório
responsavel_id    BIGINT               FK para usuarios, opcional

problema          TEXT                 NOT NULL
observacao        TEXT                 Opcional
status            VARCHAR(20)          NOT NULL, padrão ABERTO
aberto_em         TIMESTAMPTZ          NOT NULL, automático
atualizado_em     TIMESTAMPTZ          Atualizado pela aplicação
excluido_em       TIMESTAMPTZ          NULL; exclusão lógica

Regras:
- Solicitante identificado no backend pelo usuário autenticado.
- Responsável poderá permanecer NULL até ser atribuído.
- Status permitido: ABERTO, EM_ANDAMENTO ou FECHADO.
- Apenas administradores poderão alterar informações administrativas.
- Exclusão será lógica.

13.4. Entidade Atendimento
Tabela: atendimentos

Campo           Tipo PostgreSQL      Regra
id              BIGINT               PK, identidade automática
chamado_id      BIGINT               FK para chamados, obrigatório

observacao      TEXT                 Opcional

Exemplos de ações:
- CHAMADO_ABERTO.

O histórico deverá ser gerado pelo backend e não poderá ser alterado por

14. REGRAS DE INTEGRIDADE E JPA
======================================================================

14.1. Relacionamentos JPA previstos

Usuario       @OneToMany -> Chamado como solicitante
Usuario       @OneToMany -> Chamado como responsável
Categoria     @OneToMany -> Chamado
Chamado       @ManyToOne -> Usuario solicitante
Chamado       @ManyToOne -> Usuario responsável
Chamado       @ManyToOne -> Categoria
Chamado       @OneToMany -> Atendimento
Chamado       @OneToMany -> HistoricoChamado
Atendimento   @ManyToOne -> Usuario responsável
Historico     @ManyToOne -> Usuario autor

14.2. Anotações previstas

@Entity                 Identifica uma entidade JPA.
@Table                  Define a tabela.
@Id                     Define a chave primária.
@GeneratedValue         Configura geração do identificador.
@Column                 Configura a coluna.
@ManyToOne              Define relacionamento muitos para um.
@OneToMany              Define relacionamento um para muitos.
@JoinColumn             Define a coluna de relacionamento.
@Enumerated             Mapeia enumerações.
@PrePersist             Executa lógica antes da inserção.
@PreUpdate              Executa lógica antes da atualização.
@Transactional          Define uma transação.

14.3. Cuidados técnicos

- Evitar CascadeType.REMOVE nas entidades que possuem histórico.
- Não utilizar exclusão física em registros relacionados.
- Utilizar DTOs para não expor diretamente as entidades JPA.
- Evitar relacionamentos bidirecionais desnecessários.
- Utilizar FetchType.LAZY quando adequado.
- Evitar consultas N+1.
- Preservar a integridade referencial.
- Definir explicitamente as regras de exclusão e atualização das chaves.

15. PAGINAÇÃO E FILTROS
======================================================================

Objetivo: permitir que o administrador consulte chamados sem carregar todos
os registros do banco de dados de uma só vez.

Filtros previstos:
- ID do chamado.
- Nome do solicitante.
- Categoria.
- Status.
- Responsável.
- Data inicial.
- Data final.

Recursos Spring Data JPA:
- Pageable.
- Page<T>.
- PageRequest.
- Sort.

Exemplo de endpoint:
GET /api/chamados?page=0&size=10&sort=abertoEm,desc

O retorno deverá apresentar conteúdo da página, número da página,
quantidade de registros por página, total de páginas e total de elementos.

A pesquisa deverá respeitar as permissões: usuários comuns consultam apenas
seus próprios chamados; administradores podem consultar todos os chamados.

16. AUDITORIA E TRANSAÇÕES
======================================================================

16.1. Auditoria

Registrar as operações relevantes:
- Abertura de chamado.
- Atualização de informações.
- Alteração de status.
- Alteração de responsável.
- Registro de atendimento.
- Encerramento.
- Reabertura.
- Exclusão lógica.

Cada registro deverá identificar o usuário que executou a operação, a ação,
o campo alterado quando aplicável, o valor anterior, o novo valor e a data.

16.2. Diferença entre atendimento e auditoria

ATENDIMENTO:
Registra o que foi feito para resolver o problema, incluindo observação,
solução, responsável e data.

AUDITORIA:
Registra as operações feitas no sistema, incluindo quem alterou dados,
qual campo foi alterado, o valor anterior, o novo valor e quando ocorreu.

Os dois registros são diferentes e deverão ser preservados separadamente.

16.3. Transações

Utilizar @Transactional nas operações que atualizam múltiplas entidades.

Exemplo de encerramento:
1. Registrar atendimento.
2. Atualizar o status do chamado.
3. Registrar auditoria.
4. Confirmar a transação.

Se alguma etapa falhar, todas as alterações da transação deverão ser
revertidas para evitar inconsistências.

17. VALIDAÇÕES E TRATAMENTO DE ERROS
======================================================================

17.1. Bean Validation

@NotNull     Impede valor nulo.
@NotBlank    Impede texto nulo, vazio ou composto apenas por espaços.
@Size        Limita tamanho de um valor.
@Email       Valida formato de e-mail, quando utilizado.
@Pattern     Valida um padrão específico.
@Valid       Dispara validações do objeto recebido.

17.2. Regras de negócio no Service

O Service deverá verificar:
- Existência do usuário.
- Existência do chamado.
- Categoria ativa.
- Responsável válido e ativo.
- Permissão para executar a operação.
- Status permitido.
- Solução obrigatória no encerramento.
- Proteção do último administrador.
- Regras de exclusão lógica.

17.3. Tratamento de exceções

Utilizar @RestControllerAdvice e @ExceptionHandler.

Situação                         HTTP
Operação realizada               200 OK
Registro criado                  201 Created
Dados inválidos                  400 Bad Request
Não autenticado                  401 Unauthorized
Sem permissão                    403 Forbidden
Registro inexistente             404 Not Found
Conflito de dados                409 Conflict
Erro interno                     500 Internal Server Error

As respostas de erro deverão ser padronizadas e não deverão expor senhas,
segredos, consultas SQL ou detalhes internos desnecessários.

22. RECOMENDAÇÕES TÉCNICAS
======================================================================

1. Separar responsabilidades: Controllers recebem requisições, Services
   executam regras de negócio e Repositories acessam o banco.

2. Utilizar DTOs: não expor diretamente as entidades JPA nas respostas da API.

3. Proteger senhas: utilizar BCrypt e nunca armazenar senhas em texto puro.

4. Utilizar exclusão lógica: preservar relacionamentos e históricos.

5. Utilizar transações: garantir consistência em operações de atendimento.

6. Utilizar paginação: evitar consultas excessivamente grandes.

7. Auditar operações: registrar quem realizou cada alteração.

8. Utilizar Flyway: manter o histórico das alterações do banco.

9. Criar testes: validar cada funcionalidade antes de avançar.

10. Evitar complexidade desnecessária: implementar somente o que o sistema
    realmente precisa.

11. Proteger endpoints no backend: não confiar apenas nos controles da
    interface.

12. Preservar histórico: evitar exclusão física de chamados, atendimentos e
    registros de auditoria.

23. SCRIPT SQL INICIAL - POSTGRESQL
======================================================================

Observação: este é um script inicial de referência. Em um projeto com Flyway,
separe as instruções em migrations versionadas. Revise as regras e os tipos
antes de utilizar em produção.

CREATE TABLE usuarios (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nome VARCHAR(150) NOT NULL,
    login VARCHAR(150) NOT NULL UNIQUE,
    senha VARCHAR(255) NOT NULL,
    perfil VARCHAR(20) NOT NULL,
    ativo BOOLEAN NOT NULL DEFAULT TRUE,
    criado_em TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    atualizado_em TIMESTAMPTZ,
    excluido_em TIMESTAMPTZ,
    CONSTRAINT ck_usuario_perfil
        CHECK (perfil IN ('USER', 'ADMIN'))
);

CREATE TABLE categorias (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nome VARCHAR(100) NOT NULL UNIQUE,
    ativa BOOLEAN NOT NULL DEFAULT TRUE
);

CREATE TABLE chamados (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    solicitante_id BIGINT NOT NULL,
    categoria_id BIGINT NOT NULL,
    responsavel_id BIGINT,
    local VARCHAR(150) NOT NULL,
    problema TEXT NOT NULL,
    observacao TEXT,
    status VARCHAR(20) NOT NULL DEFAULT 'ABERTO',
    aberto_em TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    atualizado_em TIMESTAMPTZ,
    excluido_em TIMESTAMPTZ,
    CONSTRAINT fk_chamado_solicitante
        FOREIGN KEY (solicitante_id)
        REFERENCES usuarios(id) ON DELETE RESTRICT,
    CONSTRAINT fk_chamado_categoria
        FOREIGN KEY (categoria_id)
        REFERENCES categorias(id) ON DELETE RESTRICT,
    CONSTRAINT fk_chamado_responsavel
        FOREIGN KEY (responsavel_id)
        REFERENCES usuarios(id) ON DELETE RESTRICT,
    CONSTRAINT ck_chamado_status
        CHECK (status IN ('ABERTO', 'EM_ANDAMENTO', 'FECHADO'))
);

CREATE TABLE atendimentos (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    chamado_id BIGINT NOT NULL,
    responsavel_id BIGINT NOT NULL,
    observacao TEXT,
    solucao TEXT NOT NULL,
    realizado_em TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_atendimento_chamado
        FOREIGN KEY (chamado_id)
        REFERENCES chamados(id) ON DELETE RESTRICT,
    CONSTRAINT fk_atendimento_responsavel
        FOREIGN KEY (responsavel_id)
        REFERENCES usuarios(id) ON DELETE RESTRICT,
    CONSTRAINT ck_atendimento_solucao
        CHECK (LENGTH(TRIM(solucao)) > 0)
);

CREATE TABLE historico_chamado (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    chamado_id BIGINT NOT NULL,
    usuario_id BIGINT NOT NULL,
    acao VARCHAR(50) NOT NULL,
    campo_alterado VARCHAR(100),
    valor_anterior TEXT,
    valor_novo TEXT,
    criado_em TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_historico_chamado
        FOREIGN KEY (chamado_id)
        REFERENCES chamados(id) ON DELETE RESTRICT,
    CONSTRAINT fk_historico_usuario
        FOREIGN KEY (usuario_id)
        REFERENCES usuarios(id) ON DELETE RESTRICT
);
